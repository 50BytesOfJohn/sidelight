## Additional actionable source findings

### T1 — P2: an unsuccessful replacement attempt suppresses an outstanding deletion failure

**Locations:** `Sources/Sidelight/Widgets/OpenRouter/OpenRouterService.swift:371–374` and `:407–418`. **Opus: Medium.** Additional unresolved S1 status/authority race; distinct from known queued cancellation and durable withdrawal.

**Trigger:** Remove begins, withdrawing the credential and showing the entry form while the queued delete is suspended. Start saving a replacement; validation fails (or validation succeeds but the replacement write fails). The save attempt incremented `keyChanges`, despite never committing a credential change. When the original delete returns false, its `change == keyChanges` guard drops the failure. `keyRemovalFailed` stays false and `hasKey` stays false even though deletion did not succeed and no replacement was saved. The UI loses Remove Again/the withdrawal explanation. In-session use remains correctly withdrawn; restart use is the separate known pending issue.

**Recommendation:** distinguish supersession of validation/admission from supersession of a committed storage/authorization outcome. A failed candidate must not erase the current deletion result. Retain the failure/withdrawal status until deletion succeeds or a later credential operation actually commits, while never letting an old failure overwrite a successful newer save. Extend the existing fake-store ordering tests with a held failed delete followed by failed validation and failed replacement storage.

### T2 — P2: details-to-details geometry changes recreate pre-session restoration rights

**Locations:** `Sources/SidelightCore/Avoidance/ReservationTransition.swift:158–174`, especially `:163`; `Sources/Sidelight/Panel/PanelCoordinator.swift:240–241`; pass3 ordinary bookkeeping `Sources/Sidelight/WindowAvoidance/WindowAvoider.swift:321–331`. **Opus: High.** S3 is fixed for ordinary callbacks but remains incomplete for reservation changes.

Pass3 correctly prevents `remember` from creating a details baseline. However, the generic transition still assigns `kept[new.role] = window` whenever there is no eligible baseline, including **details → details**. Changing the originating panel side while details remains open takes exactly that path. New or user-modified windows can regain the restoration rights the ordinary path now correctly refuses.

**Concrete source trace:** on a 1440-point display, open left details (width 360). A window created during that session at x=1000, width=400 is clear of it and has no baseline. Change the main panel to the right; details moves to the right strip x=1080…1440. Smart avoidance shifts the window to x=672, width=400 and stores x=1000 as a details baseline. Close to a 200-point right main strip: because that stored baseline was not snapped to the returning edge, close restores/plans from x=1000 and yields x=832, width=400. The current new-window contact at the right-details boundary minus 8 should instead follow to the right-main boundary minus 8, retaining the current far edge: x=672, width=560 if accepted. Its supposed pre-details frame never existed.

**Recommendation:** make baseline creation respect session provenance on all transition paths, not just everyday avoidance. A same-session details geometry change must not give a new/changed window a general pre-session restore layer. Preserve valid unchanged layers and necessary new-strip pushes; keep current-contact follow eligible without inventing history. Test left↔right changes while open for preexisting unchanged, new, and user-modified windows, followed by close and hide. No live window movement was performed here.

### T3 — P2: shared manual pacing timestamps admission, not the deferred request, and drains without readmission

**Locations:** `Sources/Sidelight/Widgets/OpenRouter/OpenRouterService.swift:150–164,589–596`; interacting scheduler `Sources/Sidelight/Services/RemoteResource.swift:100–105`. **Opus: High.** Introduced by S4's manual-action scheduler.

**Trigger A:** an automatic balance fetch completes at t=0. At t=1, the first manual balance click is admitted and records `lastManualAction = t=1`, but the resource's own 15-second floor delays its actual request until t=15. At t=16, Load More Keys is admitted immediately because fifteen seconds passed since the click. Its request can send one second after the manually initiated balance request. The connection floor therefore does not bound the actual manual request groups it promises to pace.

**Trigger B:** a queued action's t=15 callback is delivered late (busy main actor or wake). A later manual action is admitted first after the gap expires. The old callback then unconditionally calls `manualActionTaken()` and runs its queued actions without checking the new deadline. Different resource actions can dispatch together despite the later admission. The main actor prevents simultaneous mutation; it does not make a delayed callback's earlier eligibility remain true.

The post-key-read rejection/Retry-After recheck is correct and prevents sends under an established server hold. This finding concerns the local shared manual floor, not a demonstrated server-cooldown bypass. Batching duplicate intents can be coherent, but running every queued closure together is not proof of spacing separate request groups.

**Recommendation:** coordinate the actual dispatch of manual request groups with resource-local eligibility and recheck the common deadline when draining. Preserve one gesture's balance/activity/key-preflight group; coalesce repeated equivalent intents and keep distinct groups bounded. Do not add fifteen seconds between the preflight and activity belonging to one gesture. Typed pending intents are preferable to an unbounded array of arbitrary closures because they expose group identity, current demand and cancellation. Keep automatic freshness independent and retain the server hold at every send boundary. Tester needs delayed resource eligibility plus late-drain/next-click traces, not just click timestamps.

### T4 — P2: queued key-page actions can run after the picker disappears while public demand keeps the service alive

**Locations:** `Sources/Sidelight/Widgets/OpenRouter/OpenRouterService.swift:157–164,175–198,509–535`; owner `Sources/Sidelight/Widgets/OpenRouter/OpenRouterCreditsSettingsEditor.swift:76–84`. **Opus: Medium/High.** New delayed-action lifetime path; related to S5 cooling.

**Trigger:** a Credits key picker and Models catalogue are open/visible. A second Load More/Retry click is queued inside the shared gap. Close the picker/editor and cool the Credits panel, leaving Models visible and the Credits widget configured. `keepsAccountData` remains true, and public demand keeps `isEnabled` true. `apply` stops balance/activity policies but neither drops this pending key action nor tracks whether any picker needs it. The delayed closure calls `loadNextKeyPage`, which has no picker-lifetime gate, and sends private work after its consumer is gone. The same path can retain an already-started key-page task. Balance refresh closures at least consult each resource's nil policy; key-page closures do not.

**Recommendation:** give explicit key-picker work a visible owner/demand lifetime separate from catalogue service lifetime. Cancel queued/active page work when its last picker owner disappears; validate that ownership before delayed dispatch and after awaits alongside credential/list generations. Preserve the configured account cache and permit an actually visible picker to work even if its panel is hidden. This is a resource-lifetime correction, not the already-known isolation restriction on opening the real manager in QA. Test with retained public demand, closed picker, delayed page/retry, and multiple picker owners.

### T5 — P2: successful credential save strands a mounted key picker with no reload path

**Locations:** `Sources/Sidelight/Widgets/OpenRouter/OpenRouterCreditsSettingsEditor.swift:39–40,76–84`; `Sources/Sidelight/Widgets/OpenRouter/OpenRouterService.swift:384–388,459–464,501–505`. **Opus: Medium.** Additional unresolved credential-resume lifecycle.

**Trigger:** select One key while no management credential is saved. The mounted picker performs its sole `onAppear` load and receives `.noKey`. Save a valid management credential using the form above it. Save clears the list to `OpenRouterKeyList()` through `keyChanged`/`forgetKeyList`, but neither the service nor the still-mounted picker reloads it. Now it is empty, with no problem and no `fetchedAt`: Try Again is absent, `hasMore` is false, and there is no Load Keys action. Selecting a chart key requires hiding/recreating the picker. Replacing a withdrawn credential while the picker stays mounted has the same issue.

**Recommendation:** reload an actively owned picker after a **committed credential generation** change, or provide an explicit load action for this empty-authorized state. A Bool-only `hasKey` change hook misses replacement where stored presence stays true. Do not unconditionally load private pages on every save with no picker on screen. Coordinate with T4's ownership. The source inference follows Apple's distinction between [appearance callbacks](https://developer.apple.com/documentation/swiftui/view/onappear(perform:)) and [value-change callbacks](https://developer.apple.com/documentation/swiftui/view/onchange(of:initial:_:)-4psgg); a body update is not a guaranteed reappearance. No native picker interaction was executed.

## Architecture, cooling and Swift source assessment

The existing partition remains worth keeping: one shared main-actor observable service, independent catalogue/balance/scoped activity resources, pure Sendable Core data/geometry, concurrent transport/normalization/Security boundaries, and one avoider/ledger owner. Pass3 introduces no singleton, Timer, detached task or second window mover. `DelayedTask` manages manual waiting and is cancelled on whole-service stop, credential change and account-data forgetting. Its synchronous closure execution stays on the app's actor; the issue is eligibility/lifetime, not a new Swift data race.

Ordinary fetch publications check cancellation and credential generation; page publications additionally check `keyListGeneration`. Removing a resource policy cancels its schedule/in-flight task and retains freshness state. Stop still preserves account cache when configured, and forgetting account data explicitly clears it. No recurring private fetch loop is introduced when policies are nil. However, public demand can keep the new private-action queue alive (T4), and queued closures lack resource identity/demand generation. Repeated clicks allocate more closures and cancel/recreate a delayed task; this is bounded by user activity but not coalesced into bounded resource intents. T3/T4 should be corrected in this scheduler, not by adding another service or wakeup loop.

Removal resets still-demanded resources, causing at most a local held/no-key result before terminal pause; it does not authorize a private send. A rejected connection may let an already-scheduled resource wake once to record the shared hold, then `.onRequest` stops its automatic loop. Already-issued requests cannot be unsent; ordinary generation guards prevent old-account publication after withdrawal/save. The known queued-write cancellation gap remains outside those fetch guards. `load` still performs normalization after transport returns before caller cancellation is checked; obsolete bounded decode work is possible, but no CPU effect was measured.

The whole-sibling gate performs synchronous AX reads. A transition enumerates frames and then rereads siblings per candidate, giving quadratic frame-read work for an app with many windows. That work is event-driven, not idle polling, and much of the pattern predates pass3. It is a native latency measurement concern; no speculative performance defect or target violation is asserted. A complete consistent per-app evidence snapshot may reduce it if measurements justify the change, while retaining conservative identity checks.

Main/details visibility observation, five-second covered-panel grace, sixty-second unseen grace, hidden clocks, fixed details geometry, logical reservations independent of alpha, close/hide content lifetimes and quit cleanup are unchanged by this pass. The contrast resolver's defaulted parameter retains prior callers/config behavior. No new configuration field or migration landed yet; the durable-withdrawal implementation must preserve released config decoding and must not be represented as already present.
